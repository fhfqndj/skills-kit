# Переразбивка и переписывание истории

Справочник к `SKILL.md`: команды для случаев, когда коммиты уже сделаны и их надо разложить иначе. Правила-гейты остаются в навыке; здесь — механика.

Общий порядок: сначала `git status` и `git log --oneline`, потом резервная ветка, потом переписывание, сверка дерева и проверка каждого коммита.

## Разъехавшиеся коммиты (ещё не запушенные)

Переразбиваются, а не подклеиваются:

```bash
git reset --soft HEAD~N
git restore --staged .
# затем коммиты по темам
git show --stat --oneline HEAD~2   # по каждому: в нём только его тема
```

Историю запушенной ветки не переписывать.

## Запушенный коммит не amend'ить

`--amend` меняет хеш, push отвечает `non-fast-forward`, а `--force` без просьбы владельца запрещён. Правку оформлять новым коммитом:

```bash
git reset --soft origin/<ветка>   # изменения остаются в индексе
git commit
git push
```

## Один файл на две темы — деление по хункам

Без интерактивного `add -p`: разбить `git diff -- <файл>` на патчи (шапка + выбранные `@@`-блоки) и применить первый перед первым коммитом:

```bash
git apply --cached p1.patch
```

Остаток файла уйдёт во второй коммит через обычный `git add`. Так файл, где твоя правка соседствует с чужой, живёт в разных коммитах.

## Каждый коммит проверять отдельно, а не только HEAD

Через worktree:

```bash
git worktree add <workdir>/wt <sha>
# прогон тестов
git worktree remove --force
```

На macOS нет `tac`: перечислять sha явно (`for sha in a1 a2 a3`) и смотреть, что число тестов растёт по ходу ветки; один упавший коммит ломает `bisect`.

В монорепо с pnpm/npm worktree — дорогой путь: `node_modules` в нём нет, и прогон начинается с установки зависимостей. Если дерево чистое (всё закоммичено), дешевле цикл по месту:

```bash
git checkout <sha>          # тесты пакета и сборка затронутого пакета, ~10 с на итерацию
git checkout <ветка>
```

Перед циклом — `git status --short` пуст, иначе правки владельца уедут в чужой коммит.

## Автора коммита определяет email, а не имя

`-c user.name=<аккаунт> -c user.email=<чужой email>` даёт коммит от чужого аккаунта: локальный `git log --format='%an'` показывает нужное имя и врёт. Сверять по API:

```bash
gh api repos/<owner>/<repo>/pulls/<n>/commits --jq '[.[].author.login] | unique'
```

Если автор не тот — переписать только свою ветку и сверить дерево до/после:

```bash
# .mailmap: «<верное имя> <верный email> <старое имя> <старый email>»
git filter-repo --force --refs master..HEAD --mailmap .mailmap
# filter-repo снимает remote origin — вернуть: git remote add origin <url>
git rev-parse HEAD^{tree}     # до и после — одинаковый
git push --force-with-lease   # force — только после явной просьбы владельца
```

## Схлопывание по смыслу без интерактивного rebase

```bash
git branch backup/<ветка>-before-squash
# для каждой группы: взять дерево последнего коммита группы и собрать цепочку
git commit-tree <tree> -p <parent> -m "<msg>"
```

Так промежуточные снапшоты остаются теми же, что были в истории, а не пересобранными заново. Перед `git reset --hard <новый HEAD>` обязательно:

```bash
[ "$(git rev-parse HEAD^{tree})" = "$(git rev-parse <new>^{tree})" ] || { echo "деревья не совпали — откат"; exit 1; }
```

Соседние по времени коммиты одной темы (фича + её правки через один шаг) склеивать можно, только если они идут подряд — иначе нужного дерева просто не существует.
