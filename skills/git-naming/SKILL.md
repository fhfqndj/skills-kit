# Именование в Git

Собирает сообщения коммитов вида `[action]: comment` и имена веток `[action]/[what-it-is]` по правилам проекта.

## Когда открывать

Открывать, когда задача — создать коммит в Git, написать сообщение коммита, назвать ветку или разобрать диф и решить, как его закоммитить. Покрывает и новую работу, и переименование уже существующих коммитов.

## Локальные договорённости

- Главная ветка всегда `master` (не `main`).
- Подсказку, которую GitHub показывает после создания репозитория (`git commit -m "first commit"`, `git push -u origin main`), буквально не выполнять: ветка `master`, первый коммит — `chore: initial commit` (если владелец задал свой текст — писать ровно его, см. «Публикация в новый репозиторий»). После первого пуша выставить в репозитории default branch `master` (`gh api -X PATCH repos/<owner>/<repo> -f default_branch=master`): новый репозиторий создаётся с дефолтом `main`, которого в нём нет, и открывается как пустой.
- Начальная настройка нового репозитория (`.gitignore`, лицензия, hooks) коммитится прямо в `master`; в сформированном репозитории — только ветка и PR.
- **Ветку проверять до первой правки (`git branch --show-current`), а не после двадцатого коммита.** Задача не про настройку окружения — сразу `feature/*` (или ветка, названная владельцем), иначе серия из десятков коммитов ложится в `master`, и перекладывать её задним числом дорого.
- Если коммиты уже легли в локальный `master` — историю не переписывать: `git branch -f <feature> master`, `git checkout <feature>`, затем `git branch -f master origin/master`. Работа остаётся в feature-ветке, `master` возвращается к состоянию origin, force-push не нужен.
- Агентские коммиты идут от аккаунта, который выдал владелец репозитория.
- **`git commit` фиксирует ВЕСЬ индекс, а не только последний `git add`.** Сделанный раньше `git rm` или `git add` другой темы уезжает в следующий коммит. Перед коммитом — `git status`; удаление чужого файла из индекса — `git restore --staged <путь>` (файл остаётся удалён в дереве, но уходит из коммита).
- **Запушенный коммит не amend'ить:** `--amend` меняет хеш, push отвечает `non-fast-forward`, а `--force` без просьбы владельца запрещён. Правку оформлять новым коммитом: `git reset --soft origin/<ветка>` → `git commit` → обычный push.
- **Автора коммита на GitHub определяет email, а не имя:** `-c user.name=<аккаунт> -c user.email=<чужой email>` даёт коммит от чужого аккаунта, а `git log --format='%an'` показывает нужное имя и врёт. Сверять по API: `gh api repos/<owner>/<repo>/pulls/<n>/commits --jq '[.[].author.login] | unique'`.
- **Каждый коммит проверять отдельно, а не только HEAD:** worktree или цикл по месту; один упавший коммит ломает `bisect`.

Разъехавшиеся коммиты, деление файла по хункам, проверка каждого коммита, `filter-repo` и схлопывание через `commit-tree` — `references/history-rewrite.md`.

## Безопасность дерева и истории

- Перед правками смотреть состояние дерева (`git status`, `git diff`): в нём могут быть незакоммиченные изменения владельца. Не перезаписывать и не удалять их.
- Разрушительные операции — `reset --hard`, `checkout -- <файл>`, `clean -f`, force-push — только по явной просьбе на каждую. Чужие изменения не прятать в `stash` без разрешения.
- Git-конфиг (`user`, hooks, remotes) без запроса не менять: идентичность настраивается локально (`--local`).
- В коммит попадает только то, что относится к задаче: файлы добавлять явно по именам, а не `git add -A`, если в дереве есть посторонние изменения. Секреты, ключи, локальные конфиги и артефакты сборки — проверять перед коммитом.
- **Скан секретов перед коммитом — по именам файлов, без печати значения.** `git diff --cached -i -G'password|secret|api_key|token' --name-only` перечисляет только имена файлов, в чьём индексированном диффе нашлось совпадение; любой вывод — повод открыть эти файлы и посмотреть глазами. Саму строку с ключом не копировать ни в чат, ни в отчёт, ни в команду: значение, напечатанное один раз, уже утекло в лог вместе с командой.
- Хук отклонил коммит — исправить причину и создать коммит заново; хуки не обходить, чужие коммиты не переделывать.

## Основной принцип

Действие определять по фактическим изменениям кода, а не по названию задачи, заголовку тикета, формулировке пользователя или имени ветки. Смотреть диф и не копировать действие, предложенное пользователем, если фактические изменения указывают на другое.

## Публикация в новый репозиторий с чистой историей

Когда проект уезжает в новый (корпоративный) репозиторий и прежнюю историю показывать не надо: сначала прогнать тесты и линтеры (откатываться на старые коммиты будет нечем); внутренние документы и секреты убрать из индекса (`git rm --cached`, затем `.gitignore`), историю сохранить локальной веткой `archive/history` и не пушить её; собрать один коммит без родителей (`git checkout --orphan clean`, `git add -A`, `git commit`, `git branch -M clean master`), запушить `master` и выставить `default_branch=master`.

Текст первого коммита — как попросил владелец: при «initial commit» писать ровно эти два слова без `chore:`; префикс из общего правила — когда формат не задавали. В чужой/существующий репозиторий пушить только после явного согласия, а `--force` — только когда владелец сам просит перезаписать.

### Вариант: новое имя и копия в другой папке

Когда наружу уезжает не та же рабочая копия, а копия проекта под новым именем (демо → боевой репозиторий): все развилки спрашивать одним списком до первой команды; дерево копировать `rsync`, а не клонировать; самоупоминания переименовать; проверки прогнать до коммита; результат сверять по API, а не по выводу `gh repo create`.

Команды обоих случаев (шаги 1–5, `rsync`, `sed`, `gh repo create`, сверка по API), вопросы владельцу и правила про локальную папку, старый репозиторий, заметку в базе знаний и красный lint — `references/publish-to-new-repo.md`.

# Границы коммита

Коммиты атомарны: один коммит — одна логическая задача или изменение. Не создавать мега-коммиты, склеивающие несколько независимых задач: у каждого коммита одна логическая цель, одно основное изменение, одно подходящее действие и один комментарий, описывающий только это изменение.

Не объединять несвязанную работу только потому, что она сделана в одно время или лежит в одном рабочем дереве. Обычно это отдельные коммиты:

```text
feat: add user authentication
test: add authentication tests
docs: update authentication guide
chore: remove unused config
```

Не склеивать их в `feat: add authentication, tests, docs, and cleanup`. Несколько связанных правок кода могут попасть в один коммит, когда образуют одно цельное логическое изменение: цель — не искусственно мелкие коммиты, а фокус каждого коммита на одной логической задаче.

## Размер изменения

Размер — не бюрократия, а предсказуемость ревью и отката. Ориентиры:

- **~100 изменённых строк — норма одного коммита.** Такой коммит читается за один заход и откатывается одной командой.
- **~300 строк — только одна логическая правка.** Если 300 строк набраны из разных тем, это несколько коммитов, а не один.
- **>1000 строк — делить.** Большая правка режется на срезы по ~100 строк: каждый проверяется, коммитится, и только потом начинается следующий.
- **Документация, конфиги и генерация считаются по смыслу, а не по строкам.** 500 строк переформатированного CHANGELOG — один `docs:`-коммит; 30 строк в трёх несвязанных конфигах — три коммита. Строки — ориентир для кода, а не догма.

## Savepoint-цикл

Один проверенный срез — один коммит. Следующий срез начинается только после зелёной проверки предыдущего: реализовать срез → прогнать проверки → коммит → следующий срез.

Если срез не прошёл проверку, возвращаются только свои файлы и только к последнему коммиту:

```bash
git restore <свои-файлы>        # вернуть рабочее дерево к последнему коммиту
git restore --staged <файлы>    # снять свои файлы с индекса, если уже добавил
```

`git reset --hard` для отката среза не использовать: он сносит и чужие незакоммиченные правки, а разрушительные операции — только по явной просьбе на каждую (см. «Безопасность дерева и истории» выше). `git restore .` тоже не годится: точка вернёт всё дерево, включая работу, которая к срезу не относится.

# Сообщения коммитов

Формат строго такой:

```text
[action]: [comment]
```

**Заголовок — по-английски.** Первая строка (заголовок) коммита и имя ветки
пишутся по-английски. Если владелец задал текст сам, писать ровно его.

## Допустимые действия

- feat — добавляет новую функциональность, видимую пользователю
- fix — исправляет неверное или сломанное поведение
- ci — меняет конфигурацию или workflow CI/CD
- refactor — перестраивает код без изменения задуманного поведения
- build — меняет конфигурацию сборки, инструменты сборки или зависимости
- chore — изменения обслуживания, не подходящие под другую категорию
- docs — изменения документации
- test — добавляет или меняет тесты
- style — изменения форматирования или стиля кода без изменения поведения

## Выбор действия

Действие выбирается по основной цели фактических изменений. Правила приоритета:

1. Исправлено сломанное поведение → fix
2. Добавлена новая функциональность → feat
3. Изменён CI/CD → ci
4. Код перестроен без намеренного изменения поведения → refactor
5. Изменена система сборки или зависимости → build
6. Изменена документация → docs
7. Изменены тесты → test
8. Только форматирование или стиль → style
9. Прочее обслуживание → chore

Несколько независимых задач — не выбирать одно действие на все: сначала разделить изменения на коммиты, затем определить действие для каждого. Части одной логической задачи могут быть одним коммитом; тогда действие — по основной цели задачи. Не ставить feat просто потому, что добавился новый код, refactor — если поведение намеренно изменилось, chore — когда подходит более конкретное действие.

## Комментарий

Комментарий должен: быть не длиннее 5–6 слов, описывать суть изменения, говорить, что изменилось, а не почему, быть конкретным, в нижнем регистре, не заканчиваться точкой, обходиться без лишних слов и без деталей реализации, если без них можно обойтись.

`fix: progress bar`, а не `fix: fix the progress bar issue`. `feat: add user authentication`, а не `feat: implement a completely new authentication system`.

# Имена веток

Формат строго такой:

```text
[action]/[what-it-is]
```

## Допустимые действия

- `feature` — новая функциональность
- `fix` — исправление ошибки
- `refactor` — перестройка кода
- `release` — работа, связанная с релизом
- `docs` — документация
- `test` — тесты

## Выбор действия

Действие ветки определяется целью работы: новая функциональность → `feature`, исправление ошибки → `fix`, перестройка кода → `refactor`, работа над релизом → `release`, документация → `docs`, тесты → `test`.

Действие ветки описывает **цель работы**, а не обязательно итоговое действие коммита. Ветка может содержать несколько коммитов, но сама ветка должна представлять **одну логическую задачу или кусок работы**. Не использовать одну ветку для нескольких несвязанных задач, когда их можно разумно разделить.

## Срок жизни ветки

- **Ветка живёт не дольше одного рабочего дня.** За это время она либо вливается, либо явно разбивается на куски.
- **Дольше — делить:** кусок работы режется на ветки по срезам, каждая сливается отдельно. Долгая ветка расходится с `master`, и merge превращается в отдельную задачу с конфликтами.
- **Неизвестно, получится ли вообще, — это одноразовый эксперимент, а не долгая ветка.** Одноразовая проверка гипотезы идёт в отдельной ветке или копии, а её результат — решение, а не полугодовая ветка.

## Описание ветки

Часть `[what-it-is]` должна: быть в нижнем регистре, разделять слова дефисами, не содержать пробелов, быть краткой, описывать цель ветки, обходиться без лишних деталей и без специфичных для Git префиксов.

# Важное различие

Префиксы коммитов и веток не совпадают: коммит `feat:`, ветка `feature/`. Пары «коммит → ветка» — `references/naming-examples.md`.

# Проверка

Перед выдачей сообщения коммита или имени ветки проверить его по правилам.

### Проверка коммита

- [ ] Допустимое действие; формат «действие, двоеточие, комментарий»
- [ ] Комментарий не длиннее 5–6 слов, в нижнем регистре, без точки в конце
- [ ] Описывает фактическое изменение, без лишних объяснений
- [ ] Представляет одну логическую задачу и не склеивает несвязанные изменения в мега-коммит

### Проверка ветки

- [ ] Допустимое действие; формат «действие, слэш, описание»
- [ ] Описание в нижнем регистре, слова разделены дефисами, краткое
- [ ] Отражает фактическую цель и представляет один логический кусок работы

Если сгенерированное имя нарушает хоть одно правило — переделать его до выдачи.

# Вывод

Когда просят сообщение коммита или имя ветки — возвращать только его, если дополнительное объяснение не запрошено явно. Когда просят и то и другое:

```text
Commit: <commit message>

Branch: <branch name>
```
