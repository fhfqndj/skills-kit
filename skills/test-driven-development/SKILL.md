# Разработка через тесты (TDD)

## Обзор

Сначала тест. Увидеть, как он падает. Написать минимальный код, чтобы он прошёл.

**Основной принцип:** если вы не видели, как тест падает, вы не знаете, проверяет ли он то, что нужно.

**Нарушать букву правил — значит нарушать их дух.**

## Когда применять

**Всегда:**
- Новые функции
- Исправления багов
- Рефакторинг
- Изменения поведения

**Исключения (сначала спросить владельца):** одноразовые прототипы, сгенерированный код, файлы конфигурации.

Думаете «пропущу TDD только в этот раз»? Стоп. Это рационализация.

## Железный закон

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

Код до теста? Удалить. Начать заново.

**Без исключений:**
- Не оставлять его «как справку»
- Не «адаптировать» его, пока пишете тесты
- Не смотреть на него
- Удалить значит удалить

Писать заново из тестов. Точка.

## Сначала узнать команды репозитория

Цикл один, команды — разные. До первого теста выяснить, как тестирует **этот** репозиторий, и гонять именно его команды на каждом RED, GREEN и финальной проверке:

- **Чем собирается проект:** `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Gemfile`, `Makefile`, `Package.swift` или `project.yml` у iOS.
- **Что запускать:** обёртки из репозитория (`./gradlew`, `./mvnw`, `make test`, `npm test`, `npx vitest run`, `pytest`, `xcodebuild test`) важнее глобально установленных инструментов.
- **Как прогнать один тест** и как весь набор: это две разные команды, нужны обе.
- **Где живут тесты** и как называются файлы: смотреть соседние, а не изобретать своё.

`pytest` в примерах ниже — образец формы, а не единственный стек. Не предполагать `npm test` по умолчанию: у Go, Rust, iOS и Python команда своя, и прогон не той команды даёт зелёный отчёт о чужом коде. Команды, которые гейтят мерж, записаны в README, CONTRIBUTING и CI.

## Цикл RED-GREEN-REFACTOR

### RED — написать падающий тест

Написать один минимальный тест, показывающий, что должно происходить.

**Требования:**
- Одно поведение на тест
- Чёткое описательное имя (в имени есть «and»? Разделить)
- Настоящий код, а не заглушки (если только это не правда неизбежно) — порядок выбора двойников ниже
- Имя описывает поведение, а не реализацию

Хороший и плохой тест — `references/examples.md`.

### Проверить RED — увидеть, как он падает

**Обязательно. Никогда не пропускать.**

```bash
# Запусти конкретный тест
pytest tests/test_feature.py::test_specific_behavior -v
```

Убедиться:
- Тест падает (а не выдаёт ошибку из опечатки)
- Сообщение о падении ожидаемое
- Падает потому, что функции нет

**Тест прошёл сразу?** Вы проверяете уже существующее поведение. Исправить тест.

**Тест упал с ошибкой?** Исправить ошибку, гонять заново, пока не упадёт правильно.

### GREEN — минимальный код

Написать простейший код, чтобы тест прошёл. Не больше. Не добавлять функции, не рефакторить чужой код и не «улучшать» сверх теста.

**В GREEN допустим временный хардкод — но только как шаг к обобщению.** Зашить конкретное значение, чтобы увидеть зелёный, можно; остановиться на нём — нельзя. Перед REFACTOR хардкод обязан исчезнуть, и доказывает это **второй тест с другим входом**: он был бы красным при зашитом значении. `grep` по литералу доказательством не является — тот же литерал живёт в тесте как вход или ожидание. Пропущенный граничный случай — это поведение, а не форма: его закрывает следующий RED/GREEN, а не REFACTOR.

Сравнение «достаточно» и «лишнее» — `references/examples.md`.

### Проверить GREEN — увидеть, как он проходит

**Обязательно.**

```bash
# Run the specific test
pytest tests/test_feature.py::test_specific_behavior -v

# Then run ALL tests to check for regressions
pytest tests/ -q
```

Убедиться:
- Тест проходит
- Остальные тесты по-прежнему проходят
- Вывод чистый (без ошибок, предупреждений)

**Тест не прошёл?** Исправить код, а не тест.

**Другие тесты упали?** Чинить регрессии сейчас.

### REFACTOR — уборка

Только после зелёного: убрать дублирование, улучшить имена, вынести помощники, упростить выражения. Держать тесты зелёными всё время; не добавлять поведение.

**Если тесты упали во время рефакторинга:** откатить сразу. Шагать мельче.

### Повтор

Следующий падающий тест на следующее поведение. По одному циклу за раз.

## Не резать горизонтально

**Не** писать сначала все тесты, а потом всю реализацию: горизонтальный разрез превращает RED в «написать кучу воображаемых тестов», а GREEN — в «заставить кучу пройти», и даёт хрупкие тесты, потому что тесты проектируются раньше, чем реализация научила вас, какое поведение и какой интерфейс действительно важны. Вместо этого — вертикальные трассирующие пули: один сквозной срез поведения, который доказывает, что путь работает, учит вас интерфейсу и держит каждый следующий тест на том, что вы только что узнали. Схема WRONG/RIGHT — `references/examples.md`.

## Сколько каких тестов

Пирамида: ~80 % маленьких, ~15 % средних, ~5 % больших — пропорция отвечает, почему набор идёт минуты. Размеры, что в них писать и примеры — `references/test-strategy.md`.

## DAMP в тестах

В коде DRY обычно прав; в тестах — DAMP: каждый тест читается как фраза спецификации, без похода в общую фикстуру, чтобы понять, что он проверяет. Три строки подготовки, повторённые трижды, дешевле общей фабрики, из-за которой через месяц неясно, какие данные попали в проверку. Общая обвязка оправдана, когда собирает предметную сущность целиком (`make_run(status="running")`), а не прячет по одному параметру; одна проверка на одно поведение — тоже часть DAMP: тест с пятью утверждениями непонятно что сломал. Пример — `references/examples.md`.

## Двойники: от настоящего к моку

Порядок предпочтения — от самого честного к самому опасному: **настоящая реализация** (высшее доверие, ловит настоящие баги) → **fake** (работающая замена: база в памяти, тестовый сервер) → **stub** (отдаёт заданные данные, поведения нет) → **mock** (проверяет вызовы; только когда настоящее использовать нельзя).

Мок уместен, если настоящая зависимость медленная, недетерминированная или имеет побочные эффекты, которые нельзя откатить (внешний платёж, письмо). Мокать всё подряд — получить зелёные тесты при сломанном проде. **Для краша и отката упражнять настоящую границу:** инъекция исключения — не падение процесса, а мок транзакции — не откат в базе.

## Чек-лист проверки

Перед тем как объявить работу готовой:

- [ ] У каждой новой функции/метода есть тест
- [ ] Видел падение каждого теста до реализации, и по ожидаемой причине (нет функции, а не опечатка)
- [ ] Написан минимальный код, чтобы каждый тест прошёл
- [ ] Все тесты проходят, вывод чистый (без ошибок, предупреждений)
- [ ] Тесты используют настоящий код (заглушки — только если неизбежно)
- [ ] Набор проходит в копии проекта без `.env`, ключей и сети
- [ ] Граничные случаи и ошибки покрыты

Не все пункты отмечены? Вы пропустили TDD. Начать заново.

## Когда застряли

| Проблема | Решение |
|---------|----------|
| Не знаю, как это тестировать | Написать желаемый API. Сначала написать утверждение. Спросить владельца. |
| Тест слишком сложный | Дизайн слишком сложный. Упростить интерфейс. |
| Приходится подменять всё | Код слишком связан. Использовать внедрение зависимостей. |
| Подготовка теста огромная | Вынести помощники. Всё ещё сложно? Упростить дизайн. |

## Как гонять тесты и передавать задачу

Команду проекта гонять на каждом шаге: RED — убедиться, что тест падает, GREEN — что проходит, затем полный набор — что нет регрессий. Образец команд — в цикле выше.

### Передача субагенту

Когда отправляете субагентов на реализацию, требование TDD идёт в цель и контекст задачи:

- цель: `Implement [feature] using strict TDD`;
- контекст: шаги навыка (RED → GREEN → рефакторинг), команда тестов проекта, структура файлов;
- доступ: командная строка и файлы репозитория;
- результат: вывод прогонов тестов, а не пересказ.

Имена инструментов, запуск и делегирование различаются по хосту — смотри его документацию.

### С systematic-debugging

Баг найден? Написать падающий тест, воспроизводящий его. Пройти цикл TDD. Тест доказывает исправление и предотвращает регрессию.

Никогда не чинить баги без теста.

## Антипаттерны тестирования

Проверка заглушки вместо реального кода, проверка деталей реализации, только счастливый путь, хрупкие тесты на структуру, повторный прогон без правки — полный список с объяснениями и правильным поведением: `references/test-strategy.md`.

## Герметичность набора

Зелёный набор, которому нужны ключи, сеть или локальный `.env`, — ложное доказательство: на CI и на чужой машине он падает там, где код вообще не дошёл до сервиса.

- Тест не должен читать настоящие ключи: подставляй заглушку («пустые поля»), а конфиг — фиктивный.
- Клиенты платных сервисов создавать **лениво** (свойство, а не конструктор): ветка без обращений к сервису не требует учётных данных; иначе падает с `Missing credentials` в незадействованном месте.
- Шов под заглушку описывать протоколом (`Protocol` + `@runtime_checkable`), иначе заглушка не проходит проверку типов и `isinstance`.
- Проверять явно: прогон в копии проекта **без** `.env` и без переменных окружения (как на CI): `rsync -a --exclude .git --exclude .env <проект>/ <песочница>/` и там полный набор тестов.

## Красные флаги — СТОП и начать заново

Поймали себя на любом из этого — удалить код и начать заново по TDD: код до теста, тест после реализации, тест проходит сразу, не можете объяснить падение, тесты «позже», рационализация «только в этот раз», «я уже проверил вручную», «тесты после достигают той же цели», «оставлю как справку», «уже потрачено X часов», «TDD догматичен», «здесь другой случай».

Полный список с разбором — `references/rationalizations.md`.

## Финальное правило

```
Production code → test exists and failed first
Otherwise → not TDD
```

Без исключений без явного разрешения владельца.
